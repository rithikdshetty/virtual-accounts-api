Built like a payments backend should be

Every design decision optimizes for correctness under concurrency and money that can never silently vanish.

⚖️

Double-entry ledger

Every movement writes paired entries that net to zero. Balances are derived from SUM(entries) — there is no balance column to drift.

🔢

Integer minor units

Amounts are integers (cents, pence) plus an ISO 4217 code. Floats never touch money, so rounding errors can't accrue.

🔁

Idempotent writes

Every money-moving POST takes an Idempotency-Key. Retries replay the original response for 24h — no double charges.

🔒

Row-locked transfers

SELECT … FOR UPDATE serializes concurrent debits against the same account, so the balance check is always atomic.

📡

Signed webhooks

HMAC-SHA256 in Stripe's t=…,v1=… format, exponential-backoff retries up to 24h, then dead-lettering.

📜

Replayable events

A pull-based /events log with 30-day retention lets consumers recover from outages without losing a beat.

🧭

Cursor pagination

Stable, O(log n) cursors instead of offsets — pages don't shift when new rows are inserted mid-scan.

🚦

RFC 7807 errors

problem+json with a stable code field. Clients branch on the code, never on human-readable prose.

🏷️

Prefixed ULID IDs

acct_, tfr_, dep_… time-sortable IDs that read cleanly in logs and catch mismatches early.

Move money in three calls

Authenticate with a bearer token, create an account, fund it, then transfer. Pick your language.

# 1. Create an account (Idempotency-Key required on every write)
curl -X POST https://virtual-accounts-api.onrender.com/accounts \
  -H "Authorization: Bearer $API_KEY" \
  -H "Idempotency-Key: $(uuidgen)" \
  -H "Content-Type: application/json" \
  -d '{"customer_id": "cus_demo", "currency": "USD"}'

# 2. Fund it with a deposit (amount in minor units → 15000 = $150.00)
curl -X POST https://virtual-accounts-api.onrender.com/deposits \
  -H "Authorization: Bearer $API_KEY" \
  -H "Idempotency-Key: $(uuidgen)" \
  -d '{"account_id":"acct_…","amount":15000,"currency":"USD","rail":"ach"}'

# 3. Transfer between two virtual accounts (atomic, row-locked)
curl -X POST https://virtual-accounts-api.onrender.com/transfers \
  -H "Authorization: Bearer $API_KEY" \
  -H "Idempotency-Key: $(uuidgen)" \
  -d '{"source_account_id":"acct_A","destination_account_id":"acct_B","amount":5000}'
const BASE = "https://virtual-accounts-api.onrender.com";
const headers = {
  "Authorization": `Bearer ${API_KEY}`,
  "Idempotency-Key": crypto.randomUUID(),
  "Content-Type": "application/json",
};

// Create an account
const account = await fetch(`${BASE}/accounts`, {
  method: "POST", headers,
  body: JSON.stringify({ customer_id: "cus_demo", currency: "USD" }),
}).then(r => r.json());

// Transfer $50.00 (amounts are integer minor units)
await fetch(`${BASE}/transfers`, {
  method: "POST",
  headers: { ...headers, "Idempotency-Key": crypto.randomUUID() },
  body: JSON.stringify({ source_account_id: "acct_A", destination_account_id: "acct_B", amount: 5000 }),
});

Explicit state machines

Every resource has a constrained lifecycle. Illegal transitions are rejected, not silently absorbed.

Account

pending→ active⇄ frozen→ closed

Closing requires a zero balance. closed is terminal.

Transfer

posted| failed| reversed

Synchronous & atomic. Reversals are a dedicated endpoint, full-value only.

Deposit

pending→ posted| failed

External rail in (ACH · wire · RTP). Credits on posted.

Withdrawal

pending→ posted| failed

Debits immediately (funds reserved), then settles async.
