# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

FastAPI implementation of the Virtual Accounts API. Customers hold virtual accounts on a single master FBO bank account; balances are tracked as liability positions on an internal **double-entry ledger** (the source of truth). `OpenAPI.yaml` is the contract the implementation conforms to; see `README.md` and `NOTES.md` for the design rationale and open questions.

## Common commands

```bash
# Install (editable, with dev extras)
pip install -e ".[dev]"

# Run the dev server (auto-reload). Requires .env with DATABASE_URL, API_KEY.
uvicorn app.main:app --reload --port 8000

# Apply DB migrations (always run after pulling new revisions)
alembic upgrade head

# Create a new hand-written migration (migrations are NOT autogenerated)
alembic revision -m "short description"

# Tests — TEST_DATABASE_URL must be set in .env or conftest aborts at import.
pytest                                      # full suite
pytest tests/test_transfers.py              # one file
pytest tests/test_transfers.py::test_name   # one test
pytest -k transfer -x -vv                   # keyword + stop on first fail

# Lint (ruff is the project's dev dep)
ruff check .

# Production start (Render runs this; runs migrations then uvicorn)
./start.sh
```

`DATABASE_URL` must use the `postgresql+psycopg://` prefix (psycopg3), not `postgresql://`. Both `DATABASE_URL` and `TEST_DATABASE_URL` should point at separate databases — tests truncate tables and re-seed the FBO row between every test (see `tests/conftest.py`).

## Architecture

### Layout
- `app/main.py` — FastAPI app wiring; mounts routers and starts the webhook worker thread in `lifespan`.
- `app/routers/` — one module per resource (`accounts`, `deposits`, `transfers`, `withdrawals`, `events`, `webhook_endpoints`, `health`). Each defines an `APIRouter` and is included from `main.py`.
- `app/models/` — SQLAlchemy 2.0 ORM models. **Hand-written; kept in sync with migrations manually.** `Base` is defined in `account.py` and re-exported via `models/__init__.py`.
- `app/schemas/` — Pydantic v2 request/response models. Names mirror the OpenAPI spec.
- `app/lib/` — cross-cutting infra: `auth`, `idempotency`, `events`, `webhook_worker`, `ids`, `request_id`.
- `alembic/versions/` — hand-written migrations. `alembic/env.py` overrides `sqlalchemy.url` from `app.config.settings` so secrets stay out of `alembic.ini`. `target_metadata = None` is intentional (no autogen).
- `tests/conftest.py` — test fixtures; truncates `TABLES_TO_TRUNCATE` and re-seeds the `fbo_cash_USD` row between tests. Provides `client`, `db_session`, `auth_headers`, `active_account`, `frozen_account`, `fresh_idem_key`, and `assert_invariant_holds()`.
- `OpenAPI.yaml` — authoritative API contract. When changing an endpoint's shape, update the spec too.
- `tools/receiver.py` — local webhook receiver for manual delivery testing.

### Money & ledger model
- Money is **integer minor units** + ISO 4217 currency code. Never use floats for amounts.
- Every money movement writes **paired `LedgerEntry` rows** that net to zero. The system invariant — `sum(customer liabilities) == sum(FBO cash entries)` for each currency — is checked in tests via `assert_invariant_holds()` and must hold after every committed transaction.
- The master FBO row has id `fbo_cash_USD` (one per currency) and is seeded by migration `0002_fbo_cash_account.py` and re-seeded by `conftest._truncate_and_reseed`.
- Account balances are derived from `SUM(ledger_entries.amount)` (see `_compute_balance` in `routers/transfers.py`); there is no balance column. Transfers and withdrawals lock account rows via `SELECT ... FOR UPDATE` before reading the balance.

### IDs
- All resource IDs are `<prefix>_<ULID>` (`acct_`, `tfr_`, `txn_`, `dep_`, `wdr_`, `evt_`, `whe_`, `whd_`). Generate with `app.lib.ids.new_id("prefix")`. ULIDs are time-sortable so DB indexes stay locality-friendly.

### Idempotency
- Every POST that creates or moves money requires the `Idempotency-Key` header. Enforced by the `require_idempotency_key` async dependency in `app/lib/idempotency.py`.
- The dependency hashes the canonical-JSON request body and looks up `(api_key_hash, idempotency_key)` in `idempotency_keys`. Cached responses replay; same key + different body → 409; expired entries (>24h) are deleted and retried.
- Each endpoint must check `if idem.cached_response:` early and return the cached payload, then call `idem.store(db, response_dict, status_code=...)` before commit on the fresh path.
- Known limitation: not atomic across concurrent requests with the same key (no advisory lock yet) — documented in `idempotency.py`.

### Events & webhooks
- Business events are emitted via `app.lib.events.emit_event(db, type, data)` **inside the same DB transaction** as the underlying business write. This guarantees event-iff-event-happened (no events for rolled-back txns, no missing events for committed ones). Production at scale would use an outbox table + separate poller.
- `emit_event` also inserts `WebhookDelivery` rows (status=`pending`) for each active endpoint subscribed to the event type.
- `app/lib/webhook_worker.py` runs a **single daemon thread** started in `main.lifespan`. It polls `webhook_deliveries` every 5s (`SELECT ... FOR UPDATE SKIP LOCKED`), signs payloads with HMAC-SHA256 in Stripe's `t=<ts>,v1=<hex>` format, POSTs via httpx, and applies exponential backoff up to a 24h budget before dead-lettering. Scaling beyond one app instance requires moving this out of the process.
- For deterministic test timing, call `webhook_worker.process_once()` instead of waiting on the polling loop.

### Internal vs external rails
- Internal transfers (`/transfers`) post **synchronously** in one DB transaction: lock both accounts, debit/credit, write ledger entries, emit `transfer.posted`.
- External rails (deposits/withdrawals) use `pending → posted | failed` because real bank settlement is async. Withdrawals debit the customer account and the FBO immediately on create (funds reserved); deposits credit on `posted`.

### Auth & errors
- Single bearer token from `settings.api_key`. `app/lib/auth.require_api_key` validates and returns `sha256(key)` for downstream scoping (notably idempotency).
- All errors use the RFC 7807 `problem+json` shape with a stable `code` field. Clients branch on `code`, never on `title`/`detail`. Routers each define a local `_error(...)` helper that injects `request_id` from `request.state` (populated by `RequestIdMiddleware`).

### Database connection (Neon-specific)
The engine in `app/db.py` sets `connect_args={"prepare_threshold": None}` to disable psycopg3 server-side prepared statements. This is **required** for Neon's pooled (PgBouncer transaction-mode) endpoint — without it, queries intermittently fail with "prepared statement already exists" once connections are reused. `pool_pre_ping=True` and `pool_recycle=1800` handle Neon's idle drops.

### Sync, not async
SQLAlchemy is used synchronously; FastAPI runs sync route handlers in its threadpool. This is a deliberate v0.1 trade-off (correctness over throughput) documented in `app/db.py`. The webhook worker uses sync httpx for the same reason.

## When changing the schema
1. Write a new file under `alembic/versions/` by hand (don't autogenerate).
2. Update the corresponding ORM model in `app/models/` to match column-for-column — SQLAlchemy does not enforce this and drift causes runtime errors.
3. If a new table holds per-test mutable state, add it to `TABLES_TO_TRUNCATE` in `tests/conftest.py` in FK-safe order (children before parents).
4. Run `alembic upgrade head` against both `DATABASE_URL` and `TEST_DATABASE_URL`.
